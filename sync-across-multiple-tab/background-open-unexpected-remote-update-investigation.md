# 后台开帖后误报云端更新调查记录

## 1. 文档目的

这份文档专门记录一条低频、非必现的多标签页异常：

- 在帖子列表页启用了“后台用新标签页打开帖子”
- 一次性后台打开多个帖子
- 实际只激活并阅读其中一个
- 过一段时间后，当前页却出现“检测到云端有更新”并触发刷新或相关提示

这份文档的目标不是替代 `Phase 2 / Phase 4 / Phase 7` 正式方案，而是把当前这条问题的：

- 现象
- 已排除项
- 当前判断
- 已加诊断
- 下次复现时的取证步骤

单独保存下来，方便后续在别的设备或新的会话里继续排查。

如果需要查看基于这份调查进一步整理出的完整结论、根因分层和修复方案，可继续阅读：

- [same-device-unexpected-remote-update-findings-and-fix-plan.md](./same-device-unexpected-remote-update-findings-and-fix-plan.md)

## 2. 现象描述

用户当前使用场景：

1. 在帖子列表页启用了脚本的“后台打开帖子”能力。
2. 在列表页连续点开多个帖子，浏览器会在后台新开多个帖子标签页。
3. 用户只真正切到其中一个帖子页阅读。
4. 剩余后台帖子页从未主动激活。
5. 阅读过程中，当前页偶发出现“检测到云端有更新”之类提示，甚至刷新页面。

当前已知特征：

- 该问题不是必现。
- 当前确认只出现过极少次数。
- 发生时没有第二台设备同时浏览帖子。

## 4. 已经排除或暂时不支持的假设

### 4.1 不是自动清理旧阅读记录导致

当前用户设置是“手动清理”，不是“自动清理”。

因此：

- `cleanupOldReadProgress()` 这条链路不是本次现象的主因。
- 自动 cleanup 导致后台页启动即改本地数据的假设，当前场景下不成立。

### 4.2 不能把“没有别的电脑在用”直接等同于“云端一定没变”

当前页自己只要发生了合法阅读进度写入并推送到云端，云端版本就会变化。

所以：

- “没有第二台设备”只能排除跨设备写入
- 不能排除“本机某个标签页自己把阅读进度推上去了”

## 5. 当前调查过的核心假设

### 5.1 假设 A：后台新开页启动时被异常当成 `visible`

这是最先怀疑的一条：

- 后台新开页虽然从未被用户激活
- 但在浏览器 / 油猴 / `GM_openInTab(..., { active: false })` 的某个时序里
- 新页启动初期拿到了异常的 `document.visibilityState === "visible"`
- 进而仅靠 `visible_stable` 被误认为“真实阅读成立”

这条假设目前 **还没有被彻底证实，也没有被彻底排除**。

但已经知道：

- 它不是每次都会发生
- 即便存在，也更像低频时序问题，而不是稳定必现逻辑错误

### 5.2 假设 B：当前真正阅读的页自己把阅读进度推上去了

这条假设在现有样本里已经得到支持。

现有一份诊断样本显示：

- `阅读启动快照: page=11, vis=hidden, focus=no`
- `最近阅读确认: 2026/4/18 09:23:15 | user_interaction`
- `最近动作: background:pushed`
- `最近成功: 2026/4/18 09:23:44`

这说明在该样本里：

1. 当前页启动时并不是 `visible`
2. 当前页的阅读确认也不是 `visible_stable`
3. 而是通过真实交互 `user_interaction` 建立的
4. 随后当前页自己把阅读进度成功推到了云端

因此，这份样本 **否定了“当前这个活跃阅读页是靠异常初始 `visible` 误写进度”** 这一条。

但它 **没有** 单独证明“其他从未激活的后台页绝对没问题”，因为那份样本主要记录到了当前活跃页。

## 6. 当前真正未决的问题

现在真正还没钉死的是：

> 那些从未激活过的后台帖子页，是否会在极少数时序下拿到异常启动信号，
> 从而误进入阅读进度写入链路？

要回答这个问题，关键不是再靠回忆，而是抓住后台页自己的启动期证据。

## 7. 已经新增的诊断能力

为了解决这个“低频、非必现、容易丢现场”的问题，当前已经在 `S1Plus.js` 中补了两层诊断。

### 7.1 事件流水

同步诊断里现在有：

- `阅读调试 1..N`

它会记录最近几条阅读进度相关事件，例如：

- `rp_context_init`
- `rp_pageshow`
- `rp_visibilitychange`
- `rp_focus`
- `rp_candidate_visible`
- `rp_reading_confirmed`
- `rp_queue_write`
- `rp_last_modified`

用途：

- 用来看细节
- 适合复盘当前页最近到底做了什么

限制：

- 很容易被当前活跃页连续的 `wheel` / `interaction` 事件刷掉

### 7.2 快速摘要字段

同步诊断里还新增了：

- `阅读启动快照`
- `最近阅读确认`

用途：

- 快速判断“当前最近一次样本是不是启动异常”
- 快速判断“是 `visible_stable` 还是 `user_interaction` 通过确认”

限制：

- 它们本质上还是“最近一次”的全局字段
- 后续如果当前活跃页继续阅读，仍可能被覆盖

### 7.3 启动摘要列表

为避免后台页证据被活跃页刷掉，诊断里又进一步新增：

- `启动摘要 1..N`

这是当前最重要的取证入口。

每个帖子页会按：

- `tabId + threadId + page + startedAt`

单独保留一张“启动病例卡”，只记录该页首次发生的关键信号：

- 初始 `visibility / focus`
- 首次 `visibilitychange`
- 首次 `pageshow`
- 首次 `focus`
- 首个可见楼层候选
- 首次阅读确认
- 首次入队写入
- 首次 `read_progress` 时间戳更新

这样即使当前活跃页后来产生大量滚轮事件，后台页自己的启动证据也不会被覆盖掉。

## 8. 如何解读“启动摘要”

下次复制同步诊断时，优先看：

- `启动摘要 1`
- `启动摘要 2`
- ...

一条摘要里最需要关注的是这些字段：

- `init=visible/...`
  - 如果后台从未激活页一上来就是这个，就很可疑
- `confirm=visible_stable@...`
  - 如果后台从未激活页却出现这个，也很可疑
- `queued=yes@...`
  - 说明它真的入队了阅读进度写入
- `modified=yes@...`
  - 说明它真的触发了 `read_progress` 的本地时间戳更新

如果一个从未激活的后台帖子页出现下面这种组合，就几乎可以直接判定异常：

1. `init=visible/...`
2. `confirm=visible_stable@...`
3. `queued=yes@...` 或 `modified=yes@...`

反过来，如果一直是：

- `init=hidden/no`
- `confirm=none`
- `queued=no`
- `modified=no`

那说明这个页至少没有走进我们当前怀疑的“异常启动即误写入”路径。

## 9. 下次再次出现问题时怎么操作

如果下次又出现“检测到云端有更新”并刷新或提示，按下面顺序处理：

1. 不要先点任何“处理 / 手动同步 / 全局同步”按钮。
2. 即使页面已经刷新，也先不要慌。
   - 当前诊断存在 GM 存储里，刷新后仍然还在。
3. 刷新完成后，立刻在当前标签页打开同步设置。
4. 先点“复制诊断”。
5. 在复制完成之前，不要先切去那些从未激活的后台帖子页。

复制出来后，优先保留这些部分：

1. `最近动作`
2. `最近触发源`
3. `最近结果码`
4. `最近探测结果`
5. `阅读启动快照`
6. `最近阅读确认`
7. `启动摘要 1..N`
8. `阅读调试 1..N`

如果能再补一句现场描述，会更有帮助：

- 当时你正在看的帖子 `tid`
- 后台还挂着几个从未激活过的帖子页
- 是“先提示后刷新”，还是“刷新后你才注意到”

## 10. 专门验证“后台页启动异常”时怎么做

如果不是等问题再次出现，而是想做一次更干净的验证实验，建议按下面操作：

1. 先点“重置诊断”。
2. 停留在帖子列表页，不要先进入任何帖子。
3. 后台只打开 1 个帖子页。
4. 不要激活它。
5. 等 2 到 3 秒。
6. 直接在当前页打开同步设置并复制诊断。

这次重点不是看当前页滚轮行为，而是看新的：

- `启动摘要 1..N`

判断方式：

- 如果后台页摘要里已经出现 `init=visible/...`，很可疑
- 如果后台页摘要里已经出现 `confirm=visible_stable@...`，更可疑
- 如果后台页摘要里出现 `queued=yes` 或 `modified=yes`，基本可以判定它真的写入过

## 11. 当前状态结论

截至目前，最准确的结论是：

1. 这条问题是低频、非必现的。
2. 当前至少有一份样本说明：
   - 活跃阅读页自己能合法写入并推送阅读进度
   - 所以“没有其他设备”并不能直接推出“云端不可能变化”
3. 但真正核心的未决点仍然是：
   - 从未激活的后台帖子页会不会偶发拿到异常启动信号
4. 这个问题现在已经有足够针对性的诊断能力，不再需要只靠猜测。

## 12. 后续如果继续实现修复，优先看哪里

后续如果确认后台页确实偶发拿到异常启动信号，修复重点大概率仍会落在：

1. `Phase 2`
   - 是否需要把“真实阅读成立”的条件再收紧
   - 是否要把“后台打开的新页”显式标记为被动页
2. `Phase 4`
   - 是否还需要进一步区分“本机其他标签页造成的远端变化”和“真正外部设备带来的远端变化”
3. `Phase 7`
   - 把这条场景固化成固定回归和长期诊断入口
