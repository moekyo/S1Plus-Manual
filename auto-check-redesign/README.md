# 自动检查云端更新重构交接文档

## 1. 这份文档是干什么的

这份文档不是实现方案，也不是旧方案的延续设计稿。

它的用途只有一个：给下一个新 session 提供统一的上下文，让后续可以在一个干净的前提下重新做“自动检查云端更新”的重构计划，而不是继续沿着旧补丁链路修修补补。

## 2. 为什么这次必须重构，而不是继续打补丁

这次选择重构，不是因为想优化代码风格，也不是因为想顺手整理架构，而是因为这个问题已经反复出现了很多次。

实际现象是：

- 用户只在单一设备上本地浏览页面。
- 没有其他设备在同时浏览，也没有其他设备把新状态同步到远端。
- 也不存在有人手工直接修改远端数据。
- 但脚本仍然会时不时弹出“远程有更新”之类的提示。

这类提示在该场景下按理说根本不应该出现，所以它不是单纯的体验问题，而是“自动检查云端更新”这条运行链路在判断上不可靠。

更关键的是，这个问题不是第一次出现，也不是一两个明显 bug 修掉就结束。此前已经围绕这个功能打过很多轮补丁、做过多次局部修正和兼容处理，但问题依然会反复出现。也就是说：

- 旧实现已经经过多轮修补；
- 旧实现不是没被处理过，而是“处理过很多次仍然不稳定”；
- 再继续叠补丁，投入会越来越大，但信心越来越低；
- 因此这次的决定是：先完整拆掉旧的自动检查运行逻辑，再基于新的思路重新设计。

这就是本次重构的根本原因。后续新方案应该默认建立在“不要继续修旧链路”的前提上，而不是再去给旧链路补一层判断。

## 3. 这轮已经做了什么

本轮已经先完成了一步非常明确的清理动作：

- 删除了“自动检查云端更新”的运行时逻辑；
- 保留了设置面板里的现有 UI；
- 保留了相关设置字段的保存和回显能力；
- 不让这些 UI 继续驱动实际的自动检查行为。

换句话说，当前代码基线的状态是：

- “自动检查云端更新”的设置项还看得见，也还能保存；
- 但“每次加载检查 / 回到前台检查 / 首次可见检查 / 可见页轮询检查”这些旧运行行为已经不再执行。

这样做的目的，是先把已经不可信的自动检查链路彻底退出运行态，避免它继续制造误报，再给后续重构留出一个干净起点。

## 4. 当前代码基线的实际状态

### 4.1 已删除的内容

当前 `S1Plus.js` 中，和旧自动检查链路直接相关的运行时逻辑已经被移除，包含但不限于：

- 每次加载自动检查；
- 首次可见时的远端探测；
- 回到前台时的远端探测；
- 页面持续可见时的低频轮询；
- 前台探测后的重试、反馈、冷却、补偿等附属链路；
- 这些来源在导航栏自动同步指示器中的专属来源文案；
- 自动检查专属的测试钩子；
- 自动检查专属的回归脚本。

### 4.2 明确保留的内容

以下内容是刻意保留的，不属于本轮删除范围：

- 同步设置面板中的三段式控件；
- 问号帮助说明和现有交互文案；
- `syncPerLoadCheckEnabled`；
- `syncCheckOnReturnToForeground`；
- 可选的 `syncDeviceId`；
- 这些字段在设置中的读写、归一化、跨标签页回填。

但是要注意：

- 上面前两个字段现在只是 UI 占位和未来兼容位；
- 它们当前不再驱动任何自动检查运行逻辑。
- `syncDeviceId` 当前仍然有实际价值，但它的价值主要在“来源归因”，不是替代同步判定。

### 4.3 当前仍然保留运行能力的同步来源

当前仍然保留实际运行能力的自动同步来源，只剩下这些：

- `daily_startup`
- `background_push`
- `manual_sync`

也就是说，当前代码基线并不是“所有同步都删了”，而是只删掉了“不可靠的自动检查云端更新”这一支。

### 4.4 明确保留且不应被新方案误伤的能力

后续做新方案时，以下能力应视为现有稳定能力，不能因为重构自动检查而被顺手破坏：

- 每日首次加载时同步；
- 后台自动同步推送；
- 手动同步；
- 阅读进度相关同步行为；
- cleanup 相关行为；
- 跨标签设置同步；
- 核心数据快照收敛和恢复链路。

## 6. 还有什么没有完成

本轮完成的是“拆旧链路”，不是“新方案落地”。

所以当前还没有完成的事情包括：

- 没有重新设计新的自动检查机制；
- 没有重新定义新的触发条件、节流、去重、提示策略；
- 没有新的浏览器实机行为验收结论；
- 没有新的实现计划、阶段拆分和验收口径。

尤其需要注意的一点是：

- 当前还需要在真实论坛页面中手工确认：切到“每次加载”或“回到前台”后，页面确实不会再主动触发旧的远端更新提示。

这不是因为代码状态不明确，而是因为这部分必须在真实浏览器环境里做最终行为确认。

## 7. `sync-across-multiple-tab/` 目录现在应该怎么看

`sync-across-multiple-tab/` 目录下的大量文档和脚本，现在只能当“历史设计资料”和“问题调查参考”，不能再被当成新的实现基线。

原因很简单：

- 那个目录里的很多内容，是围绕旧自动检查实现逐步补丁、逐步扩展出来的；
- 而这次已经明确决定放弃继续修旧链路；
- 所以这些资料最多只能帮助理解历史问题、历史尝试和历史失败点；
- 它们不应该反过来约束新方案必须沿用旧结构。

对下一个 session 来说，更合适的心态应该是：

- 参考它；
- 但不要被它绑住。

## 8. 新 session 做计划时应该先回答的问题

下一个 session 在开始做实现计划之前，建议先把下面这些问题单独想清楚。

### 8.1 新方案要解决的核心目标是什么

不是“尽量更快检查到远端更新”，而是优先保证：

- 不误报；
- 不在明显不可能发生远端变更的场景下乱提示；
- 不因为补偿链路过多导致行为不可预测；
- 不为了兜底而引入更多隐式状态机。

### 8.2 新方案要不要继续保留旧的触发模型

需要重新判断：

- 是否还需要“每次加载”；
- 是否还需要“回到前台”；
- 是否还需要“页面持续可见时轮询”；
- 这些模式是否应该继续暴露给用户；
- 还是应该收敛成更少、更明确、更容易验证的模型。

### 8.3 新方案的“检查”与“同步”是否还要强耦合

旧问题反复出现，一个很大的风险点就是：

- 轻量检查；
- 远端探测；
- 自动同步；
- 提示反馈；
- 重试补偿；

这些行为在历史实现里彼此耦合得太深。

新方案在计划阶段应该认真考虑，是否应该把这些阶段拆得更清楚，避免一个环节的误判直接带出后面整串行为。

### 8.3.1 可选 device ID 在新方案里扮演什么角色

当前代码基线里已经有可选的 `syncDeviceId`，而且远端元数据也已经支持记录 writer 信息。

新方案应该明确：

- 保留 `syncDeviceId`，而且继续允许它是可选项；
- 它主要用于回答“是谁写了远端”；
- 它适合区分：
  - same-session
  - same-device
  - cross-device
- 但它不能替代：
  - `contentHash`
  - `baseContentHash`
  - `updated_at`
  - session / tab 级上下文

也就是说，`syncDeviceId` 应该是“来源归因输入”，不是“同步真相源”。

### 8.4 新方案的验收标准必须先写清楚

建议新计划一开始就明确几类场景的验收结果，例如：

- 单设备本地浏览，不应出现远端更新提示；
- 多设备切换但远端未变化，不应误报；
- 远端确实有变化时，提示或同步路径应可预测；
- 在冲突、脏状态、未保存 UI、阅读中页面等场景下，行为应有清晰规则。

如果这一步不先写清楚，后面又很容易回到“打一层补丁，观察一下”的模式。

如果是为了做新的实现计划，而不是继续写旧方案代码，建议优先阅读：

- `auto-check-redesign/README.md`：先看这份总交接文档；
- `S1Plus.js`：以当前已经删除旧运行链路后的代码基线为准；
- `DEVELOPMENT.md`：看当前开发基线说明；
- `notes.md`：只把它当历史记录和问题背景，不要当当前实现说明；
- `sync-across-multiple-tab/` 下的资料：只在需要追历史原因、历史尝试、历史失败点时查阅。

## 10. 给下一个 session 的一句话结论

这次不是“继续修自动检查云端更新”，而是“承认旧实现已经被多轮补丁证明不可靠，所以先拆掉，再从头设计一个新方案”。

后续任何计划，如果又回到围绕旧链路继续叠补丁，那大概率会重复这次之前已经发生过很多次的问题。

补充一点：

- 可选 `syncDeviceId` 应该继续保留，并在新方案中承担“来源归因”职责；
- 但任何真正的同步判定，仍然必须回到哈希、更新时间和最新本地状态。
