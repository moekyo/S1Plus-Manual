# S1 Plus 同步问题总表

## 1. 文档作用

这份文档保留完整的问题背景，用来回答两类问题：

1. 我们到底讨论过哪些问题，不能漏掉什么
2. 某个阶段为什么存在，它在解决哪一批真实现象

如果只是实现某个阶段，默认不需要把整份文档都读进上下文。

## 2. 本轮讨论中出现过的现象

1. 早上第一次打开论坛时，没有立即执行“每日首次加载”，而是在几分钟甚至十几分钟后才突然提示并刷新。
2. 页面已经开了很久，中途几乎没操作，却突然出现“检测到云端有更新，正在刷新页面...”并自动刷新。
3. 从帖子列表后台打开多个帖子后，只在其中一个标签页阅读，过了大约 3 到 5 分钟，出现红色提示：
   - “检测到云端有更新，但本地也有未处理改动。为保护数据，已暂停自动拉取，请手动同步。”
4. 点击导航栏常驻提示里的“处理”按钮后，进入的是手动同步流程，但提示里却出现了“阅读记录已自动清理”“自动清理与同步成功”等文案。
5. 用户清理阅读记录时使用的是手动模式，不是自动模式，而且删除的是另一个帖子的阅读记录，不是当前帖子。
6. 用户在当前帖子页点击导航栏提示里的“处理”时，会直觉理解成“处理当前这个帖子的异常”，但实际执行的是一次全局手动同步。

## 3. 当前已做过的局部修复

这些修复已经落地，但仍要纳入正式模型，避免后续阶段回归：

1. 启动回调不再依赖 `requestIdleCallback`。
2. 启动流程引入 freshness window。
3. 错过窗口后，不再在旧页面上补跑启动专属检查。
4. 如果存在“已顺延的每日首次同步”，下一次新页面会优先补执行。
5. 手动同步和每日首次自动同步语义已经拆开。
6. 手动同步不再写当天的每日首次完成状态。
7. 自动拉取刷新策略已补充部分日志：
   - `action`
   - `reason`
   - refresh policy
   - page type
8. stale 分支日志语义已修正：
   - 只有真的顺延了每日首次同步时，才会写对应日志

## 4. 问题清单

### 4.1 启动期同步时机问题

#### 4.1.1 `3.1.1` 每日首次同步使用 `requestIdleCallback`，触发时机漂移

- 状态：`已做局部修复`
- 现象：
  - “每日首次加载”不是在用户早上第一次打开论坛时执行，而可能在几分钟后才补触发
  - 触发时会弹提示并刷新，打断当前阅读
- 根因：
  - 启动流程原先依赖 `requestIdleCallback`，浏览器可能把该回调拖延到很晚
- 风险：
  - “首次加载”语义被破坏
  - 用户感知是“突然强刷”

#### 4.1.2 `3.1.2` 启动流程过期后，曾经仍会晚到执行启动专属检查

- 状态：`已做局部修复`
- 现象：
  - 页面已经开了半天，后来突然出现“云端有更新并刷新”的提示
- 根因：
  - 即使启动流程已经过期，代码仍可能继续执行：
    - 每次加载同步检查
    - 首次可见前台探测 `page_load_visible`
- 风险：
  - 本应只在页面刚打开时运行的动作，晚到执行并打断当前页

#### 4.1.3 `3.1.3` “顺延每日首次同步”最初把其他启动任务也一起短路了

- 状态：`已做局部修复`
- 现象：
  - 为了避免晚到触发刷新，最初的修复会在 stale 分支里直接返回
- 被误伤的后续任务包括：
  - `handlePerLoadSyncCheck()`
  - `handleInitialForegroundRemoteFreshnessCheck()`
  - Token 过期提醒
  - NUX 推荐
- 风险：
  - 只想顺延每日首次同步，结果把整个启动后续链路一起扔掉

#### 4.1.4 `3.1.4` 每日首次同步顺延后，存在长期饥饿风险

- 状态：`已做局部修复，但仍建议纳入重构`
- 现象：
  - 浏览器长期挂起页面时，原本可能出现“每次都顺延，但永远等不到真正执行”
- 风险：
  - 顺延状态存在，但补偿路径优先级不足

#### 4.1.5 `3.1.5` 手动同步不应替代每日首次自动同步

- 状态：`已做局部修复`
- 现象：
  - 手动同步成功后，曾经会把当天的每日首次同步也视为已完成
- 风险：
  - 手动同步提前吞掉“每日首次自动同步”的语义

#### 4.1.6 `3.1.6` 顺延状态的导航栏指示语义不准确

- 状态：`已做局部修复，但仍建议统一重构`
- 现象：
  - 每日首次同步被顺延时，导航栏里曾显示成“后台同步待处理”等容易误解的状态
- 风险：
  - 自动同步状态来源不清，用户无法判断到底是哪类同步被延后

### 4.2 自动拉取刷新与提示语义问题

#### 4.2.1 `3.2.1` “检测到云端有更新，正在刷新页面...”文案过于宽泛

- 状态：`Phase 6 已处理`
- 现象：
  - 用户看到“云端有更新”时，很容易理解成“另一台设备改了云端”
- 实际可能表示：
  - 当前页面的本地快照落后于云端
  - 同一台机器上的其他标签页先推了云端
  - 阅读进度自动合并后需要刷新
- 风险：
  - 用户很难知道是跨设备、当前页过时，还是本机多标签页状态差异
- 当前处理：
  - 自动拉取 / 自动刷新文案已按场景区分：
    - 云端备份较新
    - 云端变化但已自动合并阅读进度
    - 启动期强制使用云端覆盖本地
    - 云端变化但当前标签页本地状态未稳定
    - 真正需要人工决策的全局冲突

#### 4.2.2 `3.2.2` 自动刷新前的诊断信息不足

- 状态：`已做局部补充，但仍建议扩大`
- 已补充：
  - `action`
  - `reason`
  - refresh policy
  - page type
- 仍缺：
  - 触发源
  - 页面可见性
  - 本地 / 远端 / 基线哈希摘要
  - 是否存在阅读进度 pending / debounce
  - 是否存在 cleanup 标记

### 4.3 前台远端探测与可见页轮询问题

#### 4.3.1 `3.3.1` 前台 follow-up sync 复用了“启动安全模式”

- 状态：`Phase 3 已处理`
- 现象：
  - 当前页在前台远端探测命中更新后，会复用 startup 模式的自动同步路径
- 直接后果：
  - 一旦当前页本地也有改动，就会得到 `skipped_push_on_startup`
- 风险：
  - 不同触发源共用了“启动期保护”语义，前台轮询、多标签阅读、页面恢复等场景都会被误判成“启动期冲突”

#### 4.3.2 `3.3.2` 可见页活跃轮询会在约 4 分钟后暴露问题

- 状态：`仍待重构`
- 现象：
  - 用户反馈不是一打开帖子就提示，而是看了大约 3 到 5 分钟后才出现红色提示
- 根因：
  - 可见页活跃轮询间隔是 4 分钟
- 风险：
  - 用户会误以为“阅读过程中突然出错”，而不是“轮询把旧状态暴露出来了”

#### 4.3.3 `3.3.3` 前台轮询命中的 `skipped_push_on_startup` 不应直接弹红提示

- 状态：`Phase 4 已处理`
- 现象：
  - 当前逻辑会把这类结果直接升级成：
    - “检测到云端有更新，但本地也有未处理改动。为保护数据，已暂停自动拉取，请手动同步。”
- 风险：
  - 对真实用户来说像是高严重度冲突
  - 但很多时候只是：
    - 多标签页中的暂时性阅读进度差异
    - 前台轮询与本地防抖撞车
    - synthetic read progress 与云端已有变更重叠

#### 4.3.4 `3.3.4` 前台探测与可见页轮询没有显式感知阅读进度的 pending / debounce 窗口

- 状态：`Phase 4 已处理`
- 现象：
  - 当前页的阅读进度可能还在：
    - 待持久化状态
    - 同步防抖状态
  - 但前台探测和 visible poll 仍会发起 follow-up safe sync
- 风险：
  - 系统会在“本地状态尚未稳定”的窗口里过早比较本地与远端
  - 临时差异会被误放大成：
    - `skipped_push_on_startup`
    - 红色冲突提示
    - 甚至全局暂停

### 4.4 阅读进度跟踪自身的问题

#### 4.4.1 `3.4.1` 线程页一加载就启动阅读进度跟踪

- 状态：`Phase 2 已处理`
- 风险：
  - 即使用户还没有真正开始阅读，也会立刻进入“可能写阅读进度”的状态

#### 4.4.2 `3.4.2` 首轮 `IntersectionObserver` 回调后会无条件安排保存

- 状态：`Phase 2 已处理`
- 风险：
  - 仅仅是页面渲染完成、DOM 被观察到，就可能安排一次本地阅读进度写入

#### 4.4.3 `3.4.3` 没有真实可见楼层时，会回退到主楼记录

- 状态：`Phase 2 已处理`
- 风险：
  - 会生成 synthetic read progress
  - 用户并没有真实读到那个位置，却被记录成“已读”

#### 4.4.4 `3.4.4` 后台打开的帖子标签页也可能制造本地改动

- 状态：`Phase 2 已处理`
- 现象：
  - 用户从帖子列表后台打开多个帖子，但并没有逐个去阅读
- 风险：
  - 这些标签页仍可能因观察器与 fallback 逻辑，先写入本地阅读进度
  - 多标签页场景下，本地平白多出“未处理改动”

#### 4.4.5 `3.4.5` 阅读进度写入没有明确区分“真实阅读”与“初始化噪声”

- 状态：`Phase 2 已处理`
- 缺失信息包括：
  - 是否发生在可见页面
  - 是否发生在后台标签页
  - 是否用户已经真正滚动或停留
  - 是否来自主楼 fallback
- 风险：
  - 同步层只能把它一律当成“本地真实改动”

### 4.5 多标签页协作问题

#### 4.5.1 `3.5.1` 一个标签页的“本地较新”会放大成全局暂停

- 状态：`Phase 3 已处理`
- 风险：
  - 一个标签页的局部问题，冻结所有标签页的自动同步

#### 4.5.2 `3.5.2` 当前多标签页状态模型缺少“页级”和“线程级”边界

- 状态：`Phase 3 已处理`
- 现象：
  - 现在很多状态都是全局键
- 风险：
  - 任何局部差异都可能污染全局同步决策

#### 4.5.3 `3.5.3` 切换到前台和可见页轮询叠加，容易放大旧状态

- 状态：`Phase 4 已处理`
- 风险：
  - 如果页面在后台期间已经生成 synthetic local dirty，`visibilitychange/pageshow` 和 visible poll 都会重复把同一个问题暴露出来

#### 4.5.4 `3.5.4` 多标签页红提示与 cleanup 快捷分支可能串联，进一步掩盖真正根因

- 状态：`Phase 6 已处理`
- 现象：
  - 当前帖子页先因为多标签页阅读 / 轮询问题出现红色同步提示
  - 用户随后点击导航栏“处理”
  - 但如果之前删过别的帖子的阅读记录，手动同步又会跳到 cleanup 快捷分支，显示“自动清理完成”
- 风险：
  - 用户看到的最终处理结果，不再对应最初触发红提示的真实根因
- 当前处理：
  - 手动同步对比弹窗会把“原始触发原因”和“另有 cleanup 记录”并列展示。
  - cleanup provenance 来自别的帖子时，UI 会明确说明那只是本次全局同步的附带比较信息，不代表当前帖子被自动清理。

### 4.6 清理阅读记录语义与同步分支问题

#### 4.6.1 `3.6.1` 自动清理模式本身没有失效

- 状态：`已澄清`
- 结论：
  - 不是“自动模式偷偷执行了”
  - 而是后续同步把事情说错了

#### 4.6.2 `3.6.2` 手动清理与自动清理共用了同一个全局标记

- 状态：`Phase 5 已处理`
- 现象：
  - `s1p_pending_cleanup_info` 同时被以下路径写入：
    - 自动清理旧阅读记录
    - 手动删除分组阅读记录
    - 手动删除单条阅读记录
- 风险：
  - 同步层无法知道 cleanup 到底来自哪里、涉及哪些帖子
- 当前处理：
  - `s1p_pending_cleanup_info` 已升级为结构化 cleanup provenance，能区分自动清理、手动单条删除和手动分组删除。

#### 4.6.3 `3.6.3` 删除的是别的帖子，也会污染当前帖子的“处理”流程

- 状态：`Phase 5 已处理`
- 根因：
  - `read_progress` 是全局同步对象
  - cleanup 标记也是全局键，不区分具体帖子
- 风险：
  - 当前页看起来像是在“处理当前帖子的问题”，实际被别的帖子之前的手动删除污染了决策
- 当前处理：
  - cleanup provenance 现在会记录涉及的 `threadIds` 和 `initiatedFromThreadId`，当前线程无关时不得再误走 cleanup shortcut。

#### 4.6.4 `3.6.4` cleanup 快捷分支的前提过于宽松

- 状态：`Phase 5 已处理`
- 当前规则的大意：
  - 只要：
    - `pendingCleanupCount > 0`
    - 当前同步判定为 `localNewer + push`
    - 去掉 `read_progress` 后本地和云端基础数据哈希相同
  - 就直接进入“cleanup 快捷自动推送”
- 风险：
  - 它并没有验证“当前差异是否真的由 cleanup 引起”
  - 普通阅读进度更新、synthetic progress、多标签页短期分歧都可能被误吃掉
- 当前处理：
  - cleanup shortcut 已要求合法来源、有效期、线程相关性、cleanup 前后 `read_progress` 哈希与 `baseContentHash` 同时匹配。

#### 4.6.5 `3.6.5` cleanup 相关提示文案把手动删除说成自动清理

- 状态：`Phase 6 已处理`
- 风险：
  - 用户会误以为脚本又偷偷执行了一次自动清理
- 当前处理：
  - cleanup 文案现在会按 provenance 来源区分：
    - 自动 cleanup
    - 手动删除
    - 来源不确定的阅读记录变更

#### 4.6.6 `3.6.6` 导航栏“处理”按钮的作用域与用户心智不一致

- 状态：`Phase 6 已处理`
- 实际行为：
  - 按钮调用的是一次全局手动同步，而不是“仅处理当前帖子”
- 风险：
  - 用户会把全局同步后的 cleanup 文案误认为“这个帖子刚刚被自动清理了阅读进度”
- 当前处理：
  - 常驻提示按钮文案已显式改成 `全局同步`，并在点击后先展示 preflight，明确这不是只处理当前帖子。

## 5. 现阶段还剩什么

截至 `Phase 7`，启动期、阅读进度去噪、状态分层、probe gate、cleanup provenance、交互语义以及诊断 / 回归基线都已完成代码阶段收口：

1. 最近一次同步 / 探测决策的关键上下文已经进入统一诊断快照，复杂问题不再只能靠零散日志追查。
2. 多标签页相关脚本回归基线已经固定下来，后续同步改动可以直接复用。
3. 剩余工作主要转为真实论坛页面上的 Tampermonkey 多标签手测，用来确认这些结构性修复在浏览器交互层也完全成立。
